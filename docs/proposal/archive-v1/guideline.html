1차 서류심사를 통과하는 기획서의 구조와 섹션별 작성 기준

이 문서는 공식 심사 기준(차량 특화성·창의성·기술 활용성·사업성)을 기준으로, 기획서의 각 칸에 무엇을, 어느 비중으로, 어떤 근거와 함께 써야 하는지 정리한 작성 기준입니다. 공식 접수양식을 대체하는 목차가 아니라, 공식 문항에 내용을 배치하기 위한 설계안입니다.

01심사위원이 확인하려는 것

이번 공모전은 "기술적으로 잘 만든 앱"보다 자동차에서 써야 할 분명한 이유가 있고, 실제 서비스로 자랄 수 있는 앱인지를 봅니다. 투자 유치용 사업계획서와 목적이 다르므로 구성도 달라야 합니다.

공식 세부 배점은 비공개입니다. 30:25:25:20은 작성 우선순위를 정하기 위한 전략적 비중이며, 차량 특화성과 창의성에 설득의 55%를 집중합니다.

기획서가 답해야 하는 4가지 질문
  1. 이 문제는 어떤 운전자·동승자가, 어떤 순간에 겪는가?
  2. 이 앱이 차량 환경에서만 줄 수 있는 가치는 무엇인가?
  3. Pleos로 실제로 작동하게 만들 수 있는가? (이미 작동하는가?)
  4. 차를 타는 고객이 계속 쓸 이유는 무엇인가?

02제출물의 성격

  • 공식 접수양식 자체가 기획서입니다. 별도 자유양식 문서는 필수가 아닙니다.
  • 시연 영상·GitHub 저장소(APK)는 선택 제출물이며, 구현 산출물에는 가산점이 있습니다.
  • FAQ 기준 5번 문항이 개발 계획이며, Pleos SDK/API 활용 계획을 구체적으로 쓰도록 되어 있습니다.
  • 공식 양식에 페이지 제한이 없다면 아래 7개 항목을 5~7쪽 분량으로 압축합니다.

04섹션별 작성 기준

① 서비스 핵심 제안 — 5%

심사위원이 30초 안에 "무슨 앱인지" 이해하게 만드는 칸입니다.

반드시 포함
  • 앱 이름 + 한 문장 서비스 정의
  • 핵심 타깃 고객
  • 해결하려는 문제
  • 기존 방식 대비 차별점
  • 대표 앱 화면 1장
서비스 정의 문장 기준

아쉬움 "차량 데이터와 AI로 다양한 기능을 제공하는 플랫폼" — 기능 나열, 상황·불편이 없음

좋음 "운전자가 휴대폰을 만지지 않고도, 차량 상황에 맞는 정보를 적절한 순간에 받는 서비스" — 언제 쓰고 무엇이 사라지는지 드러남

② 타깃 고객과 문제 정의 — 15%

기능 설명보다 먼저 그 기능이 왜 필요한지를 증명합니다. 핵심은 문제가 실제로 존재한다는 증거입니다.

세부 항목작성할 내용
고객 정의연령 같은 인구통계보다 실제 이용 상황 기준으로 구체화
발생 상황주행 중·정차 중·충전 중 등 문제가 생기는 순간
기존 불편지금 고객이 이 문제를 푸는 방법과 그 한계
중요성발생 빈도, 불편의 크기, 안전·시간·비용에 주는 영향
검증 근거인터뷰·설문·관찰·공개 통계·사용성 테스트. 출처를 밝힌다

직접 조사한 인터뷰 5건이 출처 없는 대규모 시장 수치보다 설득력 있을 수 있습니다. 단, 5건을 전체 이용자 특성으로 일반화하지 않습니다.

③ 차량 특화 가치와 차별성 — 20% · 최우선

"그냥 스마트폰 앱으로 만들면 되지 않나요?"에 반박할 수 있어야 합니다. 아래 비교표를 우리 앱 기준으로 다시 작성합니다.

비교 항목스마트폰 앱Pleos 차량용 앱
사용 맥락사용자가 직접 앱 실행주행·정차 등 차량 상황과 연계
데이터휴대폰이 접근 가능한 정보 중심차량 상태 데이터와 연계
조작 방식터치 중심차량 화면 + 음성 인터페이스
서비스 가치개인 단말 중심 경험이동 상황에 맞춘 맥락형 경험
이 섹션의 3가지 핵심 질문 — 명확히 답하지 못하면 기능이 많아도 특화성 입증이 어렵습니다
  1. 차량 데이터가 없으면 핵심 기능의 가치가 얼마나 떨어지는가?
  2. 주행·정차 상태에 따라 사용자 경험이 달라지는가?
  3. 운전자의 주의 분산을 최소화하면서 가치를 주는가?

④ 핵심 기능과 사용자 시나리오 — 20%

기능 10개를 나열하지 말고, 대표 시나리오 하나를 처음부터 끝까지 보여줍니다. 실제 화면 캡처 3~5장을 씁니다.

→

→

5문제 해결 확인

각 단계(화면)마다 사용자 행동 · 앱 반응 · 쓰인 차량 데이터/SDK · 해결되는 불편 네 가지를 함께 적고, 주행 중 가능한 기능과 정차 중에만 여는 기능을 분명히 나눕니다.

⑤ Pleos 기술 구현 및 검증 — 20% · 최우선

클래스 다이어그램·디자인 패턴 설명은 후순위입니다. 심사위원이 보려는 것은 핵심 기능이 실제로 동작하느냐입니다. 공식 개발 환경에는 Vehicle, NaviHelper, FusedLocation, TextToSpeech, SpeechToText SDK 등이 안내되어 있습니다.

핵심 기능필요 기술(SDK/API)구현 상태검증 방법
예) 차량 상태 인식Vehicle SDK상태 태그에뮬레이터 테스트
예) 위치 기반 기능NaviHelper / 위치상태 태그위치 변경 시나리오
예) 서비스 고유 기능앱 로직 · 외부 API상태 태그실제 사용자 플로우
구현 상태는 반드시 셋으로 구분

구현 완료 실제 코드와 테스트 결과가 있는 기능   프로토타입 시연은 되지만 환경·데이터가 제한된 기능   개발 예정 기술 검증·개발이 남은 기능

끝내지 않은 기능을 구현했다고 쓰면 2차 시연에서 오히려 불리합니다.

⑥ 사업성 및 성장 전략 — 15%

공식 기준에는 타깃 고객, 예상 MAU, Retention Rate, 사용자 확보·서비스 확대 가능성이 명시되어 있습니다. "수익 가능성"만이 아닙니다.

항목핵심 내용
최초 타깃 시장어떤 Pleos 지원 차량 이용자부터 공략할 것인가
사용자 확보Pleos App Market에서 앱을 발견하고 설치할 이유
이용 빈도일·주·월 또는 특정 차량 이용 상황별 빈도
리텐션첫 사용 이후 다시 쓰는 계기
확장성타깃·기능·제휴·적용 범위 확대
수익 모델적합할 때만 현실적인 모델. 억지로 만들지 않는다
예상 MAU = 도달 가능 고객 × 설치 전환율 × 월간 활성화율

확인하지 못한 시장 규모·전환율은 사실처럼 쓰지 않고 "가정"으로 표시한 시나리오로 제시합니다.

⑦ 리스크와 개발 로드맵 — 5%

현실적인 문제를 인정하고 대응을 보여줍니다. SDK/API 제약, 차량별 지원 차이, 네트워크, 개인정보, 운전자 주의 분산, 주행·정차별 기능 제한 등을 다루고, 1차 제출 시점과 2차 PT 시점의 구현 범위를 나눠 일정 현실성을 보입니다.

05작성 원칙

해야 할 것
  • 고객 문제 → 차량이어야 하는 이유 → 기능 → 구현 근거 순서로 쓴다
  • 모든 기술 주장은 코드·테스트·시연으로 뒷받침한다
  • 숫자에는 출처를, 추정에는 "가정" 표시를 붙인다
  • 주행 중/정차 중 기능을 분리해 안전 설계를 드러낸다
  • 핵심 가치 한 가지를 확실히 납득시킨다
피할 것
  • 고객 문제를 정의하기 전에 기술 구조부터 설명하기
  • 기능 목록을 길게 나열하기
  • 출처 없는 시장 규모·만들어낸 수요 수치
  • 미완성 기능을 "구현 완료"로 쓰기
  • 스마트폰으로도 똑같이 되는 기능을 핵심으로 내세우기

06제출 전 자체 점검 7문항

  • 서비스를 읽고 30초 안에 어떤 앱인지 이해할 수 있는가?
  • 해결할 문제가 실제 고객에게 존재한다는 근거가 있는가?
  • 스마트폰 앱 대비 차량에서의 독자적 장점이 입증되는가?
  • 대표 사용 시나리오가 시작부터 결과까지 완결되는가?
  • SDK 활용 방식과 구현 상태가 코드·시연물과 일치하는가?
  • 예상 사용자 규모, 이용 빈도, 재방문 이유가 구체적인가?
  • 운전 안전, 개인정보, 구현 제약에 대한 대응이 있는가?
